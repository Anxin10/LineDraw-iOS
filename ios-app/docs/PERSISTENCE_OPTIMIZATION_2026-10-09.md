# 紀錄保存與進度更新優化

## 修改

- 日期編碼快取：每個 WireJSON encoder 最多保存 4,096 個 Date 對應的原始 ISO8601 字串。當時資料庫 3,077 筆活動、5,712 個日期欄位但僅 28 種日期，避免重複格式化。不改時間精度或資料版本。
- 本機保存不排序 JSON 物件欄位。WireJSON.encoder 的一般呼叫仍預設 sortedKeys，只有 LocalDatabase 原子保存使用 sortedKeys:false；JSON 內容不變，舊檔與新檔均可載入。
- 點擊前仍同步原子保存 SUBMIT_INTENT，成功回應後仍保存 SUBMITTED；未把這兩次必要寫入延後或合併。
- DatabaseWriteTiming 分出 encodeSeconds、writeSeconds；Debug 真實批次報表另記 persist 與 publish，以區分編碼、落盤和同步發布耗時。publish 只計同步指派，不包含之後 SwiftUI 的渲染。
- gate 僅在 busy 值實際改變時發布，避免每次觀察重复更新進度與 Debug 報表；暫停／恢復／停止流程不變。
- 最後加上精簡端點 nativeSeconds 到逐次診斷 nativeQuerySeconds，後續可比較 Runner 內原生查詢時間與客戶端端到端時間。此欄位的端到端实測尚未完成，不能回填到此前輪次。

各輪最多五筆未被本機紀錄阻擋的活動，關閉自動接續。不同活動與不同時間，不能把各輪差異都歸因於程式修改。秒數不含 Runner 啟動，SUBMITTED 不等於中獎。

日期快取輪保存約 0.33–0.46 秒／筆。落盤約 0.005–0.011 秒／次，JSON 編碼約 0.139–0.236 秒／次；主要為整份快照編碼，不是落盤。不排序輪四筆實際送出保存约 0.31–0.38 秒／筆，相較前一個診斷輪約 0.48–0.55 秒有所下降，但不是同一活動可重送的精確 A/B。

最後一輪第一筆有九次外部／未知前景（未人工暫停），接著首個 LINE 查詢約 4.01 秒。第 2、4 筆只有兩次查詢，但第一個查詢分別 5.62、7.85 秒；第 3、5 筆首次約 2.72、3.06 秒。這是單次觀察長尾，不能用「查詢輪數多」或「固定等待」解釋。此次舊報表沒有 nativeQuerySeconds，尚不能分清原生快照與通道／客戶端成本，沒有宣稱減少進度更新已提高整轮速度。
