# 手機端按鈕直接定位優化 — 實作與驗證範圍

日期：2026-09-29。

原始修改階段依使用者要求未執行測試。使用者後續已明確指示「開始測試」並提供新五筆活動；本輪實際結果與限制見 [build 12 驗證報告](BUTTON_LOOKUP_VALIDATION_2026-09-29.md)。

## 變更

- `LocalWDA` 優先使用唯讀 `POST /session/:id/elements`，定位方法為 WDA 原生 `predicate string`，不使用 XPath。查詢包含 App 範圍、對話框，以及符合已知抽選、加入好友、結束、領取、中獎／未中獎與阻擋文字的元素。實機發現列舉全部按鈕會碰到背景聊天室已失效的 voiceButton，因此改為必要文字查詢。
- 同一回應要求 type、label、name、value、rect、enabled、displayed。僅接受完整必要欄位與有效 App 尺寸；name／value 原本為 nil 時允許 WDA 省略。不得省略位置、可用與可見狀態。不保存、跨頁重用 element ID，也不盲點固定座標。仍點擊已核對目標的中心。
- 尚未辨識到狀態時回到完整 XML／必要時底部 OCR，快速查詢暫緩 1 秒避免每次 loading 輪詢都多查一次。這是快速查詢的冷卻，不是額外 sleep；完整辨識照常進行。
- 快速查詢最多等待 4 秒；若逾時、回應格式不完整、WDA 不支援，該工作階段停用快速查詢並走原完整辨識。stale/no-such-element 則暫緩 1 秒並先用完整辨識，避免一次換頁中的失效元素讓全輪停用。無效 session、連線中斷與取消不會當作成功。POST /elements 不在通用自動重送名單中；點擊／開網址仍不重送。
- `DeviceScreen.navigationFingerprint` 在完整與快速讀取之間採用一致的必要元素表示，切換讀取方式本身不算完成換頁。仍先確認舊優惠券關閉，且關閉後不讀取 LINE 主畫面的完整 XML，以保留 build 11 的修正。
- 抽選穩定性以目標文字、位置、種類、可用狀態與畫面尺寸為準，保留兩次連續觀察；不再因無關商品文字變化重計。回到舊頁或 SpringBoard 會清除連續觀察次數。
- 原有「保存操作意圖 → 送出一次 → 成功回應後直接下一筆」、回應不明進 REVIEW、已領取／已結束略過、禁止兌換優惠券等行為保留。

## 尺寸與 OCR

- 每次快速查詢使用當前 App 範圍決定畫面尺寸；尺寸變化清除觀察與 OCR 快取，更新 WDA 偵測中心。點擊前拒絕越界目標，過期觀察重新讀取後若尺寸已變則不送出點擊。
- 底部 40% 是優先定位與 OCR 範圍，不是固定點擊位置。快速查詢未找到底部目標時回完整辨識；完整辨識確認優惠券標題後，才容許位於畫面中下段、唯一且可用的原生按鈕。OCR 不擴大至上方盲目尋找動作。
- OCR 先按截圖實際像素尺寸裁切底部，再將裁切影像的辨識框映射至 WDA 邏輯座標。計算考慮裁切像素取整；截圖方向或長寬比不符時不使用該圖定位。強制重新辨識時不沿用舊 OCR 結果。
- 以上是實作規則，尚不能宣稱各 iPhone 尺寸、橫向、大字體、顯示縮放皆已驗證。

## 診斷

開發用速度與導覽報告增加 `phaseTimings`：`capture.targeted`、`capture.full`、`ocr.bottom`、`overlay.captureAndOCR`、`navigation.open`。既有 `wdaTimings` 保留。階段可能互相包含，不能把 phase 與 HTTP 時間直接相加。既有 source 逾時注入保留；未注入時才用正常快速查詢，以免原故障案例不再被觸發。

## 驗證項目與界線

1. Core 測試與 Debug／Release 建置。新增案例涵蓋多種尺寸、方向、缺漏回應、不可用／隱藏／越界目標、已結束／已領取、對話框、文字間空白、全形 CAPTCHA、多目標、擴展版面、換頁指紋一致與裁切座標。
2. 原生與 OCR 各自驗證，涵蓋取消、慢載入、快速查詢逾時轉完整查詢、重新讀取期間旋轉與未知點擊回應。Core 案例本身無法取代 App／Vision／WDA 整合驗證。
3. 相同五連結唯讀導覽 A/B 量測，對照 build 11 的 30.64 秒紀錄；該數字是開啟與辨識，不是五次真實抽選。
4. 經使用者允許後再做實際抽選，分開記錄冷啟動、載入、查找、點擊與下一頁耗時。不能把完整 XML 讀取原占 9 秒直接視為全部可省去。

本輪未改動 Android、Mac 輔助程式、配對／DDI、LocalDevVPN 或 WDA Runner。使用者後續提供的新五連結已更新測試區，實際測試新增 5 筆送出紀錄；原有紀錄保留。App 及即時動態 extension 的 build number 更新為 12，依既有 Team 簽署安裝。

## 實測後的策略調整

直接元素查詢在這支手機上不一定比較快。`DeviceLookupBudget` 收集至少兩次已辨識原生畫面的查詢樣本，比較最近最多三次平均時間；若直接查詢超過完整 XML 時間的 1.25 倍再加 50 ms，該工作階段改用完整查詢。只比較查詢與解析，排除前景偵測、loading、OCR；不將比較結果跨裝置或跨執行持久化。完整辨識仍使用新的目標穩定性判斷與裁切 OCR。私人診斷報告的 `lookupMode` 說明實際選用路徑。

開發用 `--device-test-batch` 僅在 Debug、正常宣告已接受、手機模式且清單恰為當前內建五筆時，透過正式佇列執行並保留原有防重抽機制；正常啟動及 Release 不會自動送出。`--bottom-ocr-fixture` 只限本機 Safari fixture，遮掉原生按鈕標籤以驗證實際截圖 OCR；不套用 LINE。`--full-screen-lookup` 僅供 Debug 對照量測。

實機 OCR 修正：Vision 對 fixture 的「抽選」回傳 0.5。僅在原生優惠券標題已確認且完全符合已知操作／結果文字時，接受 >=0.5 的結果；其他辨識維持 >=0.9。低分未知文字、缺少脈絡或低於 0.5 的結果不允許操作，仍需穩定觀察及送出前重新辨識。
